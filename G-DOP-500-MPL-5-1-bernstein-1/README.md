# Bernstein

Deployment of the Poll application on Azure Kubernetes Service, from the source code to two public URLs, with one command.

```
poll --(RPUSH votes)--> Redis --(BLPOP votes)--> worker --(UPSERT)--> PostgreSQL <--(SELECT)-- result
```

`make deploy` builds the poll, worker and result images, pushes them to a private Azure Container Registry, and installs the Helm chart `charts/bernstein` on the cluster, with Traefik as the public entry point. How each piece works and why it was chosen: [docs/](docs/README.md) and the [ADRs](docs/adr/README.md).

## Prerequisites

- An Azure subscription with an **AKS cluster** (any cluster, it does not have to come from this repository), and Owner rights (or equivalent) on its resource group. A container registry is optional: the deploy creates one if `ACR_NAME` does not exist.
- Tools: `az`, `kubectl`, `helm`, `jq`, `git`, and Docker with `buildx` to build the images. With [Nix](https://nixos.org/), `nix develop` (or direnv with `.envrc`) provides all of them except the Docker daemon.

To create our own cluster and registry instead, see [docs/terraform.md](docs/terraform.md) (`infra/bootstrap/bootstrap.sh`, then `infra/terraform`).

## Credentials: what to set, and where

Nothing secret is in the repository. Two things are supplied at deploy time, in the shell that runs `make deploy`:

| What | How | Where it ends up |
|---|---|---|
| Azure credentials | `az login` (interactive), or `az login --service-principal -u <app-id> -p <secret> --tenant <tenant>` | The Azure CLI session; the script then runs `az aks get-credentials` to write the cluster into the kubeconfig |
| `POSTGRES_PASSWORD` | `export POSTGRES_PASSWORD='<choose one>'`: any string, chosen by you | Passed to Helm through a pipe (not the command line, not a file), stored only in the Kubernetes Secret `postgres-credentials` of the release ([docs/postgres.md](docs/postgres.md)) |

The Redis password is generated by the chart on the first install and kept across upgrades. Nothing to set.

The cluster and registry are identified by three more variables, which are not secret:

```sh
export AKS_RESOURCE_GROUP=<resource group of the cluster>
export AKS_NAME=<cluster name>
export ACR_NAME=<registry name, without .azurecr.io>   # existing, or a new globally unique name
```

They can also be written once in `.env` at the repository root (gitignored), as `export KEY=value` lines without quotes: `make` reads it. Every variable, including the optional ones: [docs/deploy.md](docs/deploy.md#use).

## Deploy

```sh
git clone <this repository> && cd <it>
az login
export POSTGRES_PASSWORD='...' AKS_RESOURCE_GROUP=... AKS_NAME=... ACR_NAME=...
make deploy
```

The command creates the registry if needed, lets the cluster pull from it, builds and pushes the images, installs the Gateway API CRDs and Traefik if they are missing, then installs or upgrades the release and waits until every pod is Ready. It ends with the public URLs:

```
poll:   http://poll.<ip>.nip.io
result: http://result.<ip>.nip.io
```

`<ip>` is the external IP of the Traefik load balancer, also shown by `kubectl -n traefik get svc traefik`. Running `make deploy` again with nothing changed changes nothing.

## Update without downtime

Change the code of one application in `poll-application/`, committed or not, and run `make deploy` again. Only the changed service gets a new image and rolls out, one pod at a time, with no failed request ([docs/deploy.md](docs/deploy.md#uncommitted-changes), [ADR-0005](docs/adr/0005-zero-downtime-rolling-updates.md)).

To prove it, run the checker in another terminal during the update; it requests both pages continuously and reports every error:

```sh
./scripts/zero-downtime-check.sh http://poll.<ip>.nip.io http://result.<ip>.nip.io
```

`make zdt-demo` does the whole scenario in one command ([docs/zero-downtime-check.md](docs/zero-downtime-check.md)).

A failed update is rolled back automatically. To go back by hand: `helm history bernstein -n bernstein`, then `helm rollback bernstein <revision> -n bernstein`.

## Tear down and cost

- `make destroy` uninstalls the release. The PostgreSQL and Redis disks are kept (and billed); `DELETE_PVC=1 make destroy` deletes them with the data.
- `make cluster-stop` / `make cluster-start` deallocate and restart the nodes of our cluster, which is what saves money. Prices and the budget: [docs/cost.md](docs/cost.md).

## Troubleshooting

| Symptom | Cause and fix |
|---|---|
| `error: <VAR> is not set` | Export the variable listed above. |
| `docker buildx is not installed` | Install the buildx plugin of your Docker (Arch: `pacman -S docker-buildx`, Debian/Ubuntu: `docker-buildx-plugin`). |
| `not logged in to Azure: run 'az login'` | No Azure CLI session. Check the subscription with `az account show`. |
| `registry <name> is not in this subscription and its name is taken` | Registry names are global: choose another `ACR_NAME`. |
| Pods in `ImagePullBackOff` | The cluster cannot pull from the registry. The script grants it with `az aks update --attach-acr`, which needs Owner rights; run it by hand otherwise. |
| Pods `Pending` | Not enough CPU or memory on the nodes: `kubectl describe pod <pod> -n bernstein` shows why. The chart's requests are in [docs/resources.md](docs/resources.md). |
| `exec format error` | Image built for the wrong CPU. The script always builds `linux/amd64`. |
| No external IP after the deploy | The load balancer is still being created: `kubectl -n traefik get svc traefik -w`. |
